# 用 3 小时给 SaaS Help Center 造一个翻译站：一次在 Atoms 上的 dogfooding

> 发布：2026.01.31  ·  阅读时长：约 14 分钟
> 关键词：本地化 / 术语库 / Vibecoding / Atoms / 出海

---

## TL;DR：如果你只看 30 秒

1. **3 小时总耗时里，AI 真正在 coding 的时间只有大约半小时。** 剩下两个半小时是产品判断的时间。vibecoding 真正的瓶颈是脑子，不是代码生成。
2. **整个项目的总成本是 57.89 Credits，折算下来不到 2 美元。** 同样需求走传统开发流程，保守估计几千美元起步。
3. **vibecoding 的成本峰值在 UI 的反复打磨，不在底层逻辑重构。** 这意味着开发节奏应该是：先把数据模型和核心逻辑跑通，UI 留到最后一次性收掉。
4. **多语言翻译质量的关键不在"翻译模型多强"，而在"术语库是不是被当成硬约束而不是字典"。** AI 知道术语不能改之后，它会主动重写所有非术语的部分来让句子合法。
5. **产物形态必须跟着使用者的能力边界走，不能跟着开发者的偏好走。** 同样的功能，对一个会 AI Coding 的人最优解是 skill，对一个只用浏览器的人最优解是网页工具。

下面是这 5 条结论各自的完整故事，以及一份我从这次实践反推出来的 9 阶段产品设计 SOP，外加一份针对 skill 形态的架构设计 SOP。

## 起点：我接手用户服务的第一周

那段时间我刚接手 Atoms 的用户服务工作。每天的例行动作之一，是登进我们的官方 Help Center，扮演一个完全不熟悉产品的人，去和智能客服一来一回地聊。

很快我就遇到了第一个不对劲的地方。我用中文针对同一个功能换了几种问法，发现智能客服每次给出的答案都引用了不同的源文档，而这些源文档在描述同一个概念的时候用词不一样。我反查历史文档求证，确实如此：同一个英文功能 Race Mode，在不同的中文文章里被翻译成了三种不同的中文，"极速模式"、"竞赛模式"、"竞速模式"。智能客服没法把它们识别成同一个东西，所以无论用户问哪一种，得到的回答都只覆盖了一小块。

这是一个很小的发现。但它让我开始想，如果中文已经是这样，那剩下的十三种语言会怎样？我们的产品出海覆盖 14 个语种，按这个逻辑往外推，每一个语种都可能在做同样的事情，只是没有人专门去注意。

我先把发现的这个具体问题贴给团队里一直在维护 Help Center 的同事，请她改一改。她改完之后我又发现了另一处类似的，再贴给她改一遍，再发现另一处。这样来回了几次之后我意识到，这不是几篇文档的零星问题，而是一笔系统性的累积问题。

更要紧的是同事这边的情况。她当时正在主导多语言相关的工作，每周本来就要花大量时间去对齐 Help Center 的各语种内容。我每发现一处问题就让她去改一处，她每改一处就意味着她在已经饱和的工作量上又被加了一层。这件事对她来说是日常工作里非常具体的一种消耗。

我跟她聊了一下她的工作流程，她把卡点拆给我听。

第一，我们当时用的 Help Center 平台 Intercom 不支持多语言文章的自动同步。每写一篇英文原文，14 个语种要她手动一篇一篇贴进去。

第二，Intercom 不支持 Markdown 排版，不支持外部文档导入，不支持 AI 语义搜索定位，也不支持全局关键词替换。意味着即便她维护了一份术语对照表，也没法一键应用回历史文章。要修一个用词，她得手动打开每一篇相关文档，一处一处改。

第三，机翻加人工对齐的工作量在 14 个语种、上百篇文档的规模下注定追不上产品的节奏。新功能上线之后，每个语种都各翻各的，等到她有空回来对齐的时候，新的不一致又出现了。

这确实不是一个 Excel 能解决的问题。

## 这件事比想象的难

把同事的情况听完之后，我心里大致排了一下，这件事至少要解决三件事。

第一是术语一致性。同一个概念在 14 个语种里都必须有唯一译法，并且这个译法要能跨文章生效。一旦同一概念在不同文章里被译成不同的词，用户的认知就崩了，他不知道两个词是同一个东西，更不知道该搜哪一个。这不是用词偏好的问题，是品牌专业感和搜索可达性的问题。

第二是平台限制。Intercom 这种 SaaS 助手平台把内容生产卡得很死，不支持外部导入，不支持全局替换。所以无论用什么工具去翻译，最后的产物必须是可以直接复制粘贴回 Intercom 编辑器的纯文本。任何依赖 Markdown 渲染、依赖 API 写回的方案都行不通。

第三是地道度。SaaS 文档不是文学作品，但它对"读起来像母语者写的"有刚需。机翻痕迹会让用户瞬间失去信任，尤其在付费场景下。

这三件事，通用翻译工具能解决一部分，但都不是为这个场景而生的。DeepL、GPT、Crowdin、Lokalise 解决的是"翻译准确"，不是"术语一致 + 风格地道 + 工作流可批量"。

## 为什么这件事值得做到底

我顺手翻出之前写过的一篇笔记。多语言对出海产品的价值远不止"让用户能看懂"。同一款工具在不同语言市场的流量分布是天然错开的，别人没做过的语种，对你就是无竞争流量。一个英文里卷到死的关键词，到了俄语、韩语、土耳其语市场可能基本没有竞争对手。多语言不是功能加分项，它本身就是一条独立的流量来源。

但前提是质量得过得去。机翻一时省事，但被用户发现是机翻的那一刻，所有 SEO 和品牌投入会一起失效。所以我需要的工具必须既快又准，快到可以每周维护，准到可以直接上线。

## 一个我没走通的方案：直接对接 Intercom API

写代码之前我先想过一条更工程化的路径：能不能直接对接 Intercom 的 API，让翻译产物从外部工具直接写回 Intercom 后台，连复制粘贴这一步都省掉。

我去查了一下 Intercom 当时开放的 API 接口和权限模型，评估了一下改造成本和我当时能调动的资源，最后判断这条路在那个时间点上不可行，就不了了之了。

放弃 API 方案之后，问题反而清晰了。既然不能从源头改造 Intercom，那就接受 Intercom 是流程的终点，让中间多出一个可以批量处理、可以管理术语、可以直接吐出干净文本的工具，让同事的工作流变成"原文，翻译站，复制粘贴，Intercom"。

复制粘贴这一步还是会让她累，但这是当时能找到的最短路径。

## 为什么是 vibecoding，为什么是 Atoms

接下来要决定怎么做。

如果是我自己来维护这件事，最快的路径其实不是再造一个翻译站，而是把所有文档拉成 markdown，然后用 AI Coding 在文件层面整体迭代，术语统一、风格调优、批量重译，全部在我自己的工作流里跑完。这个路径对一个会用 AI Coding 的人来说效率最高。但对同事来说不可行。她的工作流必须经过 Intercom，她不会写代码，她也没有时间去学一套新的开发工具链。

所以我需要的是一个对她来说零门槛的产物：一个浏览器里能打开的网页工具，前面是输入框和语言选择，后面是带格式的翻译结果，可以直接复制粘贴。底层的术语库、AI 调用、风格规则她不需要看见，也不需要理解。

既然是这样一个轻量的内部工具，那它的开发本身也应该轻量。我决定用 vibecoding 来做。也正好 Atoms（atoms.dev）自己就是一个 vibecoding 平台，我就在 atoms.dev 上做，给自己来一次 dogfooding。

下文里出现的所有"Atoms"、"在 Atoms 上"、"Atoms 的 Credits 定价"等表述，指的都是 atoms.dev 这个产品。

## 3 小时，和半小时

整件事从坐下来开始，到工具能跑通，前后加起来大约 3 小时。

但这 3 小时里，AI 实际在 coding 的时间只有大约半小时。

剩下的两个半小时是什么？是我在思考产品形态、写需求描述、看输出结果、想下一步要改什么、然后再写一段新的描述喂给 AI。AI 收到描述之后真正生成代码的时间很短，每一轮十几秒到几十秒不等。瓶颈从来不在生成代码本身，瓶颈在我作为产品经理的脑子。

这是我做完这件事之后最想强调的一组数字。它颠倒了一个常见的误解：vibecoding 的核心不是"让 AI 帮你写代码"，而是"让人不再被代码本身拖慢"。代码生成的时间从原本的 80% 压缩到 20% 不到之后，剩下的瓶颈一定是产品判断本身。这意味着用 vibecoding 工作的人必须把自己的脑子从工程师模式切换到产品经理模式，因为工程实现已经不再是问题，问题是你能不能想清楚要做什么。

## 开发过程：10 个版本的迭代

3 小时里我大概迭代了 10 个版本。复盘一下每一版在干什么。

**V1** 是把基础架子搭起来。一个输入框，一组语言选项，一个翻译按钮，把 Gemini 接进去能跑通一轮翻译。

**V2** 是质量校准，这一版做了一件后来被证明非常关键的事情。我让 Gemini 翻译完之后，再让另一个 AI 去审查这份译文。审查 AI 给出的反馈非常具体：法语版的某些句子用词太英语化，缺少正式敬称；德语版的指令句缺介词，是不合语法的写法；阿拉伯语版需要 RTL 布局，标点位置不对；亚洲语言的敬语层级用得不对。

这一轮审查给了我一份非常有价值的清单。我意识到不同的语言族在 SaaS 文档场景下各有各的"机翻痕迹"症状，不能用一套通用的 prompt 处理所有语种。我把这份清单整理成 system prompt 里的语言族规则（后面会展开），从这一版开始翻译质量上了一个台阶。

**V3** 引入全局术语库。设计的核心思路是术语库一次定义、到处生效。用户在设置里维护一个全局库，翻译时这个库会自动作用于每一次翻译请求，AI 必须按照库里规定的译法处理对应的英文术语。

**V4** 重构了术语库的管理界面。这一版我把术语库做成了可视化编辑器加 CSV 双向流通的组合形态。可视化编辑器是折叠卡片，每个英文术语展开后是 14 个语种的输入框，旁边有进度条显示翻译完成度。CSV 双向流通让用户可以在 Excel 里舒服地批量编辑，导入导出一键完成。这两个东西后来证明是整个产品最值钱的设计。

**V5** 解决 schema 问题。我在 prompt 和代码里都加了一条硬约束：动态列识别。系统不预设支持哪些语言，而是读取上传的 CSV 表头，自动识别有哪些语种。这意味着以后想加第 15 种、第 16 种语言，只要在 Excel 里加一列，填好翻译，重新上传，系统就会自动注册新语种，不需要任何代码改动。

**V6** 完善 CSV 批量导入导出的 UI。这一版的 Credits 消耗是整个项目的峰值，比底层逻辑的重构还高，让我意识到 vibecoding 的成本大头其实在 UI 细节，不在数据模型。

**V7 到 V10** 基本都是 UI 打磨。术语弹窗样式、语言选择 checkbox、翻译结果布局重构、阿拉伯语的 RTL 渲染。唯一一个值得记录的细节是 RTL：阿拉伯语是从右往左书写的，如果不做特殊处理，标点和数字会出现在错误的位置。我在 prompt 里明确要求阿拉伯语输出带 dir="rtl" 属性，并在前端给阿拉伯语 tab 加了对应的 CSS 渲染。这件事提醒了我，做出海产品 CJK 不是终点，RTL 才是真考验。

## 这个工具最值钱的一块设计

这部分我想多写两段，因为它是整个项目里最值得拿出来讲的。

术语库通常被理解成一张查找替换表，英文 Agent 对应中文"智能体"，机器在原文里逐个替换。这种做法在简单场景里能用，但它有两个问题。

第一，不处理变形。Agents 是复数，简单查找替换会把它替成单数的"智能体"。阿拉伯语里的复数变形更复杂，单纯替换会出语法错误。

第二，不重写句子。术语替换进去之后，周围的句子常常需要调整介词、语序、性数配合。比如英文 Click Dashboard，逐字翻成德语是 Klicken Sie Dashboard，少了介词 auf，是病句。

我在 system prompt 里把术语库的角色重新定义了：术语在 14 个语种里的译法是不可改的硬约束，但句子结构可以围绕它灵活调整。

测试的时候我给了一个对模型来说不太友好的输入：chat directly with the AI Agents。

术语库里定义的是单数 Agent 对应阿拉伯语 الوكيل (Agent)。我预期 AI 会笨拙地输出一个语法不通的单数。但它给出来的是 وكلاء (Agents)，把阿拉伯语单数 الوكيل 自动复数化为 وكلاء，同时保留了术语库里规定的英文括号注释。

德语那一组也是。Click Dashboard 它输出的是 Klicken Sie auf das Dashboard，补齐了介词 auf，加上了正确的冠词 das，同时术语 Dashboard 一字未改。

这两个例子让我意识到，术语库不是字典，是约束。AI 知道这些译法不能改，但它可以重写所有非术语的部分来让句子合法。这种处理方式是逐字替换的工具永远做不到的。

回到 Race Mode 三种叫法的问题。本质上就是因为过去的工具把术语理解成"建议"，而不是"硬约束"。一旦把术语升级为约束条件，整个翻译流程的可靠性就上了一个台阶。

## 语言族风格规则

光有术语约束还不够，地道度还得靠对每个语言族的针对性调教。这就是 V2 那次 AI 审查给我的清单的价值。

我在 system prompt 里把 14 个语种按语系分了组，每组写了独立的风格规则。

**罗曼语族**包括法语、西语、意语、葡语。流畅度优先，避免短促断句；默认正式称呼（法语 Vous，西语 Usted，意语 Lei）；避免 Anglicism。

**日耳曼语族**包括德语、荷语。精准直接，指令性强；善用自然复合词；默认礼貌形式（德语 Sie，荷语 U）。

**阿拉伯语**单独成组。定义句用名词句结构，指令句用动词句结构；自然使用连词 و 和 ف；默认阳性复数；强制 RTL 布局。

**亚洲语言**包括中、日、韩、越。日语用商务敬语 desu/masu 形，韩语用 haeyo-che 形，适当时省略主语，越南语避免过度敬语。

跑完一轮模型自评，14 个语种里大部分都能给到 9 分以上的"自评一致性 + 风格匹配度"。这是模型自评不是人工双盲，所以严格来说不能拿这个数据下结论。它更像一个过线信号，告诉我可以拿真实文档去线上灰度，而不是回去重写 prompt。

## 成本盘点：3 小时，57.89 Credits

这是这次 dogfooding 最让我意外的一块。

| 阶段 | Credits |
|---|---|
| V1 初始化项目 | 3.07 |
| V2 翻译质量校准 | 2.46 |
| V3 引入全局术语库 | 4.82 |
| V4 重构术语管理系统 | 7.64 |
| V5 修复 schema 与 CSV 逻辑 | 7.41 |
| V6 批量导入导出 UI 增强 | 8.56 |
| V7 术语弹窗样式优化 | 7.03 |
| V8 语言选择功能 | 6.27 |
| V9 弹窗布局重构 | 4.45 |
| V10 翻译结果布局重构 | 6.18 |
| **合计** | **57.89** |

总耗时大约 3 小时，AI 实际 coding 时间大约半小时，总成本不到 60 Credits。按当时 Atoms 的定价折算下来不到 2 美元。

有一个反直觉的发现：我原以为 V4 的术语系统重构会是 Credits 大头，结果 V6 的"批量导入导出 UI 增强"才是峰值。这告诉我 vibecoding 的成本大头不在底层逻辑，而在 UI 细节的反复打磨。底层逻辑通常一次到位，UI 才是那个让你不停调"再往左挪 4px、那个 hover 颜色再深一点"的地方。

这个认知后来改变了我用 vibecoding 的节奏：先把数据模型和核心逻辑跑通，UI 留到最后一次性收掉，不在中间反复回调。

## 上线之后

工具开发完之后我把它交给同事用。她试了几篇之后接进了日常工作流：英文原文写完之后贴进翻译站，选 14 个语种，点翻译，一两分钟后所有译文出来，复制粘贴回 Intercom。

她原本每周要花两三天处理的多语言维护工作，被压缩到一两个小时。复制粘贴回 Intercom 这一步还是要她手动做，但相比之前那种"原文要先在脑子里翻译一遍，再自己手敲进去 14 次"的工作流，已经轻松了一个数量级。

更要紧的是术语终于一致了。新写的文档里 Race Mode 在 14 个语种里全是同一个译法，阿拉伯语的 RTL 不需要再人工调，新加一个语种只要往 CSV 里加一列。

## SOP A：用 vibecoding 解决一个真实工作流痛点的设计流程

下面这张表是我从这次实践里反向归纳出来的 9 阶段流程。它不是教科书，是我下次再做类似事情时会照着走的清单。

| # | 阶段 | 核心动作 | 注意事项 / 铁律 |
|---|---|---|---|
| 1 | 发现真问题 | dogfood 自己的产品，记录每一处不对劲；累计到至少 3 到 5 次同类型症状再判定为系统性问题 | 第一个症状的修复成本最低，最容易让人陷入"再修一个就好"的循环。强制自己等到第 N 次再动手 |
| 2 | 锁定真实使用者 | 写下使用者画像、能力边界、必经的工作流节点这三件事 | 最大的陷阱是为自己设计；假设对方完全不会任何开发工具，没有时间学新东西，工作流里有他绕不开的平台锁定 |
| 3 | 穷举可行路径并主动排除 | 至少列 4 条候选：对接对方平台 API、改使用者工具链、手工维护、造中间工具。优先尝试更轻的方案，被堵死才升级 | 跳过这步的代价是事后才发现原本有更短路径。我那次试 Intercom API 没走通才决定造工具，但这个尝试让后面的决策非常踏实 |
| 4 | 决定产物形态 | 在网页 / CLI / API / skill / 插件 / 桌面应用之间选一个；唯一依据是阶段 2 写下来的使用者能力边界 | 铁律：产物形态跟着使用者的能力边界走，不跟着开发者的偏好走 |
| 5 | 模型先于 prompt | 写第一行 prompt 之前先用真实数据反测候选模型，至少 A/B 两个，选定再卷 prompt | 在选错模型的情况下卷 prompt 是 vibecoding 里最常见的浪费。模型自身的天花板卷不动 |
| 6 | 设计核心数据模型 | 定义 schema 和 IO 接口 | 两条铁律：schema 不写死（所有支持的语种/字段/格式都从配置或数据本身动态读取）；IO 必须双向（既能导入也能导出）|
| 7 | 建立质量校准回路 | 在功能完整前，用一个独立 AI 审查另一个 AI 的输出，归纳症状清单，倒推 system prompt 里的风格规则 | 审查 AI 必须给具体反馈而不是分数。这一步是从"能跑通"到"能上线"的关键跨越 |
| 8 | UI 一次性收掉 | 数据模型 / 核心逻辑 / 质量校准全部跑通之后再做 UI，做的时候一气呵成 | vibecoding 的成本峰值在 UI 的反复打磨。中间反复回调 UI 会让成本迅速失控 |
| 9 | 交付与接入 | 亲自陪跑使用者第一次使用，记录每一处犹豫；每个犹豫位置都是下一个改动点 | 完成的标准不是"工具能跑通"，而是"使用者第二次主动打开它，不需要你提醒" |

## 如果今天再做一次

写到这里我忍不住想，如果今天让我再解决一次同样的问题，我会怎么做。

答案是我可能根本不会再造一个网页工具。

我会把这整个工作流封装成一个 skill，放进我自己的 AI Coding 工作环境里。skill 内部包含术语库、语言族风格规则、模型调用、CSV 解析。当我或者同事需要翻译一篇 Help Center 文档的时候，只需要把原文丢给 skill，参数指定要哪些语种，几秒钟之后就能拿到所有译文。这个 skill 形态比一个独立网页工具更轻、更快、更容易迭代，它甚至不需要 UI，它只需要一个明确的输入和一个明确的输出。

但当时之所以做成网页工具，是因为我必须考虑同事的接入成本。她不会用 AI Coding，她需要的是一个可以在浏览器里打开的东西。所以网页工具是当时那个具体场景下的最优解，不是抽象意义上的最优解。

这件事让我意识到一件事：vibecoding 的产物形态应该跟着使用者的能力边界走，而不是跟着开发者的偏好走。你能把一个东西做得多轻量，永远受限于你的用户能接受多重的接入成本。

## SOP B：翻译类 skill 的架构设计

如果今天我把这件事重做一遍，产物形态会从网页工具改成 skill。下面这 8 个设计决策是我会照着搭的架构。它不是 skill 的通用模板，是针对"翻译类 skill"这一类需求的取舍清单。

| # | 设计决策 | 取什么值 | 理由 |
|---|---|---|---|
| 1 | 输入接口 | 必填：原文 + 目标语种列表；可选：术语库路径、风格规则路径、审查开关；接收文件路径而非字符串；支持单文件和批量 | 文件路径方式可以处理任意大小内容，不会被参数长度限制卡住 |
| 2 | 分层架构 | 6 层从上到下：术语库加载、prompt 装配、翻译模型调用、审查模型调用、RTL/格式后处理、输出写入 | 每层只做一件事，可以单独替换任意一层而不影响其他层 |
| 3 | 术语库存储 | 单一 CSV 作为唯一真理来源；skill 启动时加载；表头动态识别支持的语种 | 禁忌：硬编码进 skill 代码。术语演化和 skill 升级必须解耦，使用者改术语不需要懂代码 |
| 4 | 模型调用抽象层 | adapter 模式适配 Gemini / Claude / GPT；至少一次重试 + 一次降级（主模型失败时回退到次模型）| 让 skill 在生产环境里不会因一次网络抖动整体失败 |
| 5 | 风格规则存储 | 独立文件（如 system-prompt.md），按语言族分块，运行时按目标语种动态拼接 | 风格规则的演化频率比 skill 本身高得多，外置才能让使用者不动代码就能编辑 |
| 6 | 审查环节 | 默认开启、可参数关闭；审查反馈注入下一轮 system prompt，**不**直接重写译文 | 保留对原始翻译的可观察性，让审查变成累积优化的过程，可以在收敛时提前停止 |
| 7 | 错误处理与可观察性 | 每语种独立错误处理；输出包含 metadata（用了哪个模型、消耗 token、审查结果、各语种耗时）| 没有 metadata 的 skill 是不可调试的 skill，也不可能持续优化 |
| 8 | 输出格式 | 直接匹配下游平台：Intercom 用纯文本、GitHub 用 Markdown、上游 skill 用 JSON | skill 不应假设输出会被再加工。这是 SOP A 第 4 条铁律在 skill 内部的具体落地 |

## 我从这件事里学到的

写完上面那两份 SOP 之后，剩下的话其实不多。

通用工具能解决 80% 的需求。但任何一个具体场景里剩下的 20%，往往才是决定能不能上线的部分。通用工具做不到这 20%，不是因为它们不够智能，而是因为它们没有为这个场景做过取舍。一个为 100 种使用场景同时优化的工具，必然在每一个具体场景里都是"还行但差点意思"。

所以当你用 AI 工具时，不要问"这个工具能做什么"，所有 AI 工具能做的事情都很多。要问"这个工具能为我的场景解决什么问题"。答案就在那些"通用工具差一口气"的地方。

而当你发现某个场景下所有现成工具都差一口气的时候，那就是 vibecoding 该上场的时候。
